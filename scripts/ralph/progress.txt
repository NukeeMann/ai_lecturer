## Codebase Patterns
- Repo dir is named `US-001` (capitalized) → cannot run `create-next-app .` directly because npm rejects capital letters in package names. Workaround: scaffold into a temp dir (e.g. `/tmp/ai-lecturer-scaffold`), then copy files into the worktree (skip the inner `.git`), and set the package name in `package.json` manually.
- `shadcn@latest` (v4.x) emits Tailwind v4 / `base-nova` style by default — incompatible with a Tailwind v3 project. Use `shadcn@2.3.0` for v3-compatible init, or write `components.json` by hand.
- Tailwind v3 baseline = `@tailwind base; @tailwind components; @tailwind utilities;` in `globals.css` + `tailwind.config.ts` with `content: ["./src/**/*.{ts,tsx,js,jsx,mdx}"]` + `postcss.config.js` with `tailwindcss` and `autoprefixer` plugins. Theme/token wiring belongs in US-002, not US-001.
- Design tokens live in `src/styles/tokens.css` (canonical source from `claude/design/source/tokens.css`) and are imported at the top of `src/app/globals.css`. Tailwind utilities resolve through CSS vars, so changing a `--*` value at runtime updates Tailwind classes too.
- Theme/accent/density are switched by `data-theme` / `data-accent` / `data-density` attributes on `<html>` (defaults: `light` / `default` / `comfortable`). Selectors in tokens.css are scoped to `:root[data-theme=…]` etc. — adding new variants means adding a new `:root[data-…="…"]` block, not a new file.
- Geist Sans + Mono are loaded via `next/font` (`geist/font/sans`, `geist/font/mono`) in `src/app/layout.tsx`. Their `.variable` classNames define `--font-geist-sans` / `--font-geist-mono`; tokens.css references those via `var(--font-geist-sans)` inside `--font-sans` / `--font-prose` / `--font-display`. Don't hardcode font names anywhere else.
- Playwright skill at `scripts/ralph/skills/playwright-skill/` ships without `node_modules`; run `npm install --no-audit --no-fund` inside it before first use. - **Vitest needs its own alias config.** `vitest.config.ts` must declare `resolve.alias = { '@': fileURLToPath(new URL('./src', import.meta.url)) }`. Vitest does NOT read `tsconfig.json#paths`. Next + `tsc` + `tsx` (used by `npm run build:schemas`) DO auto-pick it up.

- **`PythonError` shape (Pyodide 0.26).** A Pyodide exception thrown out of `runPythonAsync` is a `PythonError` (`err.constructor.name === 'PythonError'`, `err instanceof Error === true`). The headline `<Type>: <msg>` is the LAST non-empty line of `err.message`. Use `extractPythonError(err)` from `src/lib/pyodide/errorFormat.ts` to split into `{ traceback, errorType?, errorMessage? }` — do NOT lose `err.type`. `setStderr({ batched })` does NOT receive the traceback when an unhandled Python exception bubbles out: Pyodide hands the exception to the embedder (JS) instead, so `stderrBuf` stays empty and the only signal is the rejection. - **Learnings for future iterations:**
  - **Browser singleton lifecycle for puppeteer.** The launching pattern is: cache `browserRef` + `browserPromise` at module scope; `getBrowser()` returns `browserRef` if `connected`, else awaits the in-flight `browserPromise`, else launches a new one. The `disconnected` event handler clears both refs so the next `getBrowser()` call re-launches automatically. The idle timer must be `.unref()`-ed (`if (typeof idleTimer.unref === 'function') idleTimer.unref()`) — otherwise it pins the Node event loop open and the dev server can't gracefully exit. `setTimeout` returns a Timeout object whose `.unref()` is a no-op in environments without it (jest fake timers etc), hence the typeof guard.
  - **Resolving the playwright-installed chromium binary.** Playwright's binaries land in `~/.cache/ms-playwright/chromium-<rev>/chrome-linux64/chrome` (full) and `~/.cache/ms-playwright/chromium_headless_shell-<rev>/chrome-headless-shell-linux64/chrome-headless-shell`. Both work for puppeteer-core's `executablePath` config; the headless shell saves ~50MB but doesn't support Chromium DevTools-Protocol features puppeteer rarely needs. Prefer the full chrome dir if both exist (priority order: `chromium-` over `chromium_headless_shell-`). Walk with `fs.readdir` → filter prefix → look for `chrome` or `chrome-headless-shell` filename inside the linux subdirs. The version suffix (1217 etc.) varies; do not hardcode.
  - **Turbopack + puppeteer-core.** Adding puppeteer-core to a Next.js project requires `serverExternalPackages: ['puppeteer-core']` in next.config.ts — its `chromium-bidi` / `ws` transports do dynamic `require`s that Turbopack can't statically resolve (you'll see "Module not found" errors for transport-related modules at request time). Same fix pattern as pdf-parse / unzipper.
  - **Lazy `require('puppeteer-core')` inside the singleton module.** Even with `serverExternalPackages`, importing puppeteer-core at module top-level pulls it into the bundle graph and surfaces transitive resolution errors during page render. Wrap the load in a `cachedLauncher = require('puppeteer-core')` at first use (using `eslint-disable @typescript-eslint/no-require-imports` because the project still bans CJS requires elsewhere).
  - **`page.pdf()` return type.** Recent puppeteer-core returns `Uint8Array<ArrayBufferLike>` rather than Node `Buffer`. To pass it to `new Response(...)` under TS strict mode, allocate a fresh `ArrayBuffer` of `byteLength`, `new Uint8Array(ab).set(pdfBytes)`, then return `new Response(ab, {...})` — handing the Uint8Array directly trips a "BodyInit | null" type mismatch because @types/node's `ArrayBufferLike` includes `SharedArrayBuffer`, which `BodyInit` rejects.
  - **Detecting download trigger from a `window.location.href = X` navigation.** When `X` returns `Content-Disposition: attachment`, Chromium navigates to a "transient" page that immediately becomes a download — the JS context fires `pagehide` and (often) `visibilitychange → 'hidden'`. Listening for both lets you dismiss "Generating PDF…" toasts the moment the browser hands off to its download UI, with a 30s timeout as the AC-mandated fallback. Don't rely on `unload`; it doesn't fire reliably for download-triggering navigations in modern Chromium.
  - **Active-port detection in API routes.** `process.env.PORT` is set by Next when started with `PORT=… npm run dev`, but NOT when started with `next dev -p 3170`. Reading the incoming `req.url`'s port works for any active server (Next echoes the request's actual host:port back into `req.url`), and falls through to env.PORT or 3000. Order: env.PORT → req URL port → 3000.
  - **Print-friendly `react-markdown` reuse.** The Theory widget's full markdown pipeline (`remarkDirective + remarkCallout + remarkMath + rehypeKatex`) is safe to run inside a server component — none of those plugins import client-only code. The only client-only piece in TheoryWidget is the lucide icon inside its callout component, so I inlined a small `PrintCallout` (no icon) for the print page. This mirrors how staticRender.tsx (US-152) sidesteps lucide for the same reason.
  - **Vitest for the puppeteer route.** Use `__setLauncherForTesting` to swap in a fake puppeteer launcher whose `page.pdf()` returns hand-crafted `%PDF-1.4...` bytes. That keeps unit tests hermetic — no Chromium needed in CI. Reset state via `__resetForTesting` in `beforeEach` so the singleton doesn't leak between tests (a stale `browserRef.connected: true` from one test's fake browser would skip the launch in the next test). The real end-to-end with actual Chromium is verified separately via the playwright-skill browser test.
  - **Print page selector handshake.** The export route can't tell whether `goto` landed on the real print page or a Next 404 page from the URL alone (both return 200 from goto's perspective). Adding a `[data-testid="lesson-print-root"]` element and asserting it via `page.evaluate` after navigation gives a deterministic 404 signal that's independent of Next's not-found page styling. Cheaper than scraping `<title>` or response codes.
