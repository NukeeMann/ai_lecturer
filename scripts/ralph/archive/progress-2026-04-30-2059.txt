Module workers (`{ type: 'module' }`) would force us to dynamic-import the CDN URL (`import('https://cdn.jsdelivr.net/.../pyodide.mjs')`), and Turbopack's handling of external dynamic imports is bundler-specific (no `webpackIgnore` equivalent yet). Classic worker + `importScripts` is the path of least resistance.
  - **Worker file as a TS module without polluting the main-thread tsc lib.** The worker.ts file uses `export {}` to be a TS module (so `let pyodidePromise` doesn't leak into global) but **does not** add `///<reference lib="webworker" />` — that would conflict with the project's `lib: ["dom", ...]` and is unnecessary because we type the worker globals locally with `const ctx = self as unknown as WorkerScope;` where `WorkerScope` declares only the methods we actually use (`importScripts`, `postMessage`, `addEventListener`, `loadPyodide?`). This keeps `tsc --noEmit` clean across the whole project and avoids a separate tsconfig for the worker. Future workers should use the same local-shape pattern instead of `webworker` lib.
  - **`useSyncExternalStore` is the right primitive for "subscribe to a singleton with mutable state".** The naive `useState + useEffect(subscribe)` pattern was rejected by `react-hooks/set-state-in-effect` (lint error, not warning, in this project). Subscribing instead gives us: SSR-safe (server snapshot is `'idle'`), lazy worker creation (the subscribe function is what calls `getOrCreateWorker()` for the first time, post-mount), and React 18's tearing-free guarantees for free. The pattern: `subscribe(cb)` registers `cb` in a `Set<() => void>`, then immediately invokes `cb()` once so React pulls a fresh snapshot in case the singleton's status changed between the initial render and the post-commit subscription.
  - **Pyodide test-runner without pytest.** Pytest in Pyodide is heavy (fetches `pluggy`, `iniconfig`, `packaging` and the `pytest` wheel itself — adds seconds + MB to first load). The custom runner in `RUNNER_PY` is ~20 lines: `exec(user_code, ns)` once, then `exec(test.body, dict(ns))` per test inside a `redirect_stdout` block. Testing convention: the test body is a free-form Python snippet that runs `assert ...` against names defined in user code (e.g. `def add(a, b): ... ` user code; test body `assert add(1,2) == 3`). This matches the `CodeTestSchema` shape (`{name, body, hidden}`) defined in US-003. If a future story needs pytest features (parametrize, fixtures), adding pytest is one `await py.loadPackage(['pytest'])` line — but the run shape would change from "exec each body" to "write test files into a tmpfs and call `pytest.main()`".
  - **Pyodide stdout capture: `setStdout({ batched })` not `setStdout({ raw })`.** `batched` receives full lines as strings (the natural unit when Python emits via `print()`); `raw` receives byte codes one at a time and is much chattier. For our use case (capture full output, return as a single string at the end), batched is exactly right. Reset stdout/stderr handlers per-call so concurrent `run()` calls don't cross-contaminate buffers — actually, since the worker only processes one message at a time (single-threaded JS), per-call reset isn't required for correctness, but each call DOES reset to its local buffer to keep behavior predictable.
  - **PyProxy → JS conversion.** `runPythonAsync` returns Python objects as `PyProxy` references (live handles into the Pyodide runtime). To get plain JS, call `.toJs({ dict_converter: Object.fromEntries })` (the `dict_converter` option turns Python `dict` into JS `Object` instead of `Map` — `Map` is correct PyProxy default but `Object` is what JSON.stringify users expect). Always `.destroy()` the proxy after conversion to free the underlying Python reference; otherwise long-running sessions leak Python memory.
  - **Initial status is `'idle'`, not `'loading'`, until React hydrates.** `getServerStatusSnapshot` returns `'idle'` (no worker exists during SSR). On the client, the initial render happens BEFORE `useSyncExternalStore`'s subscribe phase, so the first render also sees `'idle'`. Only after the post-commit subscribe call does the worker get created and the status flip to `'loading'`. Consumers (`CodeRunner` in US-010) must treat both `'idle'` and `'loading'` as "Run button disabled" — only `'ready'` enables interaction. The state machine: `idle (SSR + first render) → loading (subscribed, worker spawning, numpy/scipy installing) → ready (Pyodide + packages loaded) → error (any throw during bootstrap)`. There's no edge from `error` back to `ready` — the AC for US-010 says "Refresh to retry."
  - **CDN cold-start time.** First `/test-pyodide` load takes ~25–35 s in headless chromium (Pyodide 0.26.4 = ~6MB compressed wasm + ~8MB JS, plus numpy ~5MB and scipy ~30MB). Subsequent loads in the same browser are <1s thanks to HTTP cache + the singleton avoiding re-init across hook consumers. Playwright tests waiting for `status === 'ready'` should set timeout ≥ 90s for safety. After first cache-warm, ~3–5s.
  - **Worker error propagation.** When the worker emits `{type:'error', error}`, the client rejects `readyPromise` AND rejects every queued `pending` request. Subsequent `run`/`runWithTests` calls will create a new pending entry but will reject immediately because `readyPromise.then(.., reject)` fires synchronously (the promise is already rejected). No infinite-pending-requests bug. The error state is sticky — there's no retry mechanism in this story; AC for US-010 will tell users to refresh.
  - **`/test-pyodide` is a `'use client'` page (not split into a `dynamic({ssr:false})` wrapper).** Server-component pages can't use `dynamic({ssr:false})` directly in Next 14+; they'd need a thin client wrapper. Since the page itself has no static / SEO content (it's a tool page), making it `'use client'` end-to-end is simpler. The "dynamic import" requirement in the AC is satisfied by the lazy worker creation inside `subscribeStatus`, not by `next/dynamic`. Real widgets (Code, Sandbox, Demo) can either follow the same pattern or use `dynamic({ssr:false})` to defer the entire widget bundle — both work; pick based on whether the widget has any SSR-able content.
  - **No package.json change needed.** Pyodide is loaded at runtime from CDN; we don't `npm install pyodide` because that pulls the wasm into the build artifact and bloats the bundle. The CDN approach has the additional benefit that Pyodide ships its own `pyodide.asm.wasm` from the same `indexURL`, so we don't have to teach Webpack/Turbopack about wasm assets.
