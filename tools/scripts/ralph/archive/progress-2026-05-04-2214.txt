## Codebase Patterns
- Repo dir is named `US-001` (capitalized) → cannot run `create-next-app .` directly because npm rejects capital letters in package names. Workaround: scaffold into a temp dir (e.g. `/tmp/ai-lecturer-scaffold`), then copy files into the worktree (skip the inner `.git`), and set the package name in `package.json` manually.
- `shadcn@latest` (v4.x) emits Tailwind v4 / `base-nova` style by default — incompatible with a Tailwind v3 project. Use `shadcn@2.3.0` for v3-compatible init, or write `components.json` by hand.
- Tailwind v3 baseline = `@tailwind base; @tailwind components; @tailwind utilities;` in `globals.css` + `tailwind.config.ts` with `content: ["./src/**/*.{ts,tsx,js,jsx,mdx}"]` + `postcss.config.js` with `tailwindcss` and `autoprefixer` plugins. Theme/token wiring belongs in US-002, not US-001.
- Design tokens live in `src/styles/tokens.css` (canonical source from `claude/design/source/tokens.css`) and are imported at the top of `src/app/globals.css`. Tailwind utilities resolve through CSS vars, so changing a `--*` value at runtime updates Tailwind classes too.
- Theme/accent/density are switched by `data-theme` / `data-accent` / `data-density` attributes on `<html>` (defaults: `light` / `default` / `comfortable`). Selectors in tokens.css are scoped to `:root[data-theme=…]` etc. — adding new variants means adding a new `:root[data-…="…"]` block, not a new file.
- Geist Sans + Mono are loaded via `next/font` (`geist/font/sans`, `geist/font/mono`) in `src/app/layout.tsx`. Their `.variable` classNames define `--font-geist-sans` / `--font-geist-mono`; tokens.css references those via `var(--font-geist-sans)` inside `--font-sans` / `--font-prose` / `--font-display`. Don't hardcode font names anywhere else.

- **`PythonError` shape (Pyodide 0.26).** A Pyodide exception thrown out of `runPythonAsync` is a `PythonError` (`err.constructor.name === 'PythonError'`, `err instanceof Error === true`). It exposes own properties `{ stack, message, type, __error_address }`. `err.type` is the Python exception class name as a string (`'ValueError'`, `'KeyboardInterrupt'`, etc.); `err.message` is the FULL formatted Python traceback ending in `<Type>: <msg>`. The headline `<Type>: <msg>` is the LAST non-empty line of `err.message`. Use `extractPythonError(err)` from `src/lib/pyodide/errorFormat.ts` to split into `{ traceback, errorType?, errorMessage? }` — do NOT lose `err.type`. `setStderr({ batched })` does NOT receive the traceback when an unhandled Python exception bubbles out: Pyodide hands the exception to the embedder (JS) instead, so `stderrBuf` stays empty and the only signal is the rejection. (Stderr IS captured for explicit `print(..., file=sys.stderr)`.)

- **Learnings for future iterations:**
  - **`page.fill` before React hydration silently no-ops the React state update.** On a cold Turbopack dev server (first /create GET takes ~2s), the input's HTML renders before useState handlers attach. `page.fill` writes the DOM value but the next `wizard-next` click sees `draft.topic === ''` and the button stays disabled. Defensive pattern: after `page.goto`, `waitForSelector` for an interactive control (suggestion chips work well as a hydration marker), add a 200-300ms `waitForTimeout`, then assert the input value via `page.waitForFunction(() => el.value === expected)` after fill. The disabled-button retry loop in the click action eats 30s before throwing.
  - **Use `:not([disabled])` selector for stage-advance clicks.** `await page.click('[data-testid="wizard-next"]')` defaults to clicking the first match, which finds the disabled button when state hasn't propagated yet. `page.locator('[data-testid="wizard-next"]:not([disabled])').first().click()` only clicks once the React-driven `disabled` attr has cleared, and converts the silent timeout into a clear waiter.
  - **`page.route(...)` interception is cleaner than spinning up a real Claude call for UI tests.** The clarify endpoint hits `selectConnector()` which would block on a real claude CLI invocation in dev. Stubbing at the network layer (`route.fulfill({ status, body })`) gives deterministic pass/fail without touching the connector module. Same pattern works for any AI-backed route the wizard adds later.
  - **Question-id dedup is necessary.** Claude has been observed returning duplicate `id: "q1"` entries when prompted for ≥10 questions. `parseClarifyResponse` dedupes by appending `-2`, `-3`, … so the React `key={q.id}` doesn't blow up. Don't rely on the prompt alone to enforce uniqueness.
  - **Cache fetched questions on the draft, not in component-local state.** Stage3Clarify keeps `clarificationQuestions` on the wizard `Draft` so back-nav from Stage 4 reuses the same array (and the user's typed answers stay aligned with it). If the questions lived in `useState` inside the stage component, every back-nav would re-fetch and the answers would either get lost or get keyed against a different set of ids.
  - **Stepper indices live in only one place.** STAGES array in `src/app/create/page.tsx` is the source of truth for the progress indicator's count and labels; the per-stage `Stage X of Y` captions are hardcoded strings inside Stage4Approval/Stage5Export. When inserting a wizard stage, grep for `Stage \\d of \\d` in src/ to catch them all.
