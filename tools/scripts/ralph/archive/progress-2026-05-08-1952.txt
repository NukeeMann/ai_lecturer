## Codebase Patterns
- Repo dir is named `US-001` (capitalized) → cannot run `create-next-app .` directly because npm rejects capital letters in package names. Workaround: scaffold into a temp dir (e.g. `/tmp/ai-lecturer-scaffold`), then copy files into the worktree (skip the inner `.git`), and set the package name in `package.json` manually.
- `shadcn@latest` (v4.x) emits Tailwind v4 / `base-nova` style by default — incompatible with a Tailwind v3 project. Use `shadcn@2.3.0` for v3-compatible init, or write `components.json` by hand.
- Tailwind v3 baseline = `@tailwind base; @tailwind components; @tailwind utilities;` in `globals.css` + `tailwind.config.ts` with `content: ["./src/**/*.{ts,tsx,js,jsx,mdx}"]` + `postcss.config.js` with `tailwindcss` and `autoprefixer` plugins. Theme/token wiring belongs in US-002, not US-001.
- Design tokens live in `src/styles/tokens.css` (canonical source from `claude/design/source/tokens.css`) and are imported at the top of `src/app/globals.css`. Tailwind utilities resolve through CSS vars, so changing a `--*` value at runtime updates Tailwind classes too.
- Theme/accent/density are switched by `data-theme` / `data-accent` / `data-density` attributes on `<html>` (defaults: `light` / `default` / `comfortable`). Selectors in tokens.css are scoped to `:root[data-theme=…]` etc. — adding new variants means adding a new `:root[data-…="…"]` block, not a new file.

Their `.variable` classNames define `--font-geist-sans` / `--font-geist-mono`; tokens.css references those via `var(--font-geist-sans)` inside `--font-sans` / `--font-prose` / `--font-display`. - **Learnings for future iterations:**
  - **`page.dispatchEvent('pointerdown'/'pointermove'/'pointerup')` does NOT create a real pointer in chromium — it's just a synthetic DOM event.** Code that calls `e.currentTarget.setPointerCapture(e.pointerId)` will throw "No active pointer with the given id is found", and any subsequent `hasPointerCapture(...)` checks return false, silently swallowing the drag. For drag tests, use `page.mouse.move(x,y); page.mouse.down(); page.mouse.move(x',y'); page.mouse.up()` — that drives the real Browser-side pointer and `setPointerCapture(1)` succeeds. Same lesson applies to any code path using the Pointer Events API (HTML drag handles, signature pads, slider widgets, etc.).
  - **Grid-template-columns transitions delay bounding-box reads.** The lesson shell uses `transition: 'grid-template-columns 180ms ease'`, so reading `boundingBox()` immediately after opening the chat captures a mid-animation width (saw 150 from the test's first read pre-fix). After clicking the toggle, `await page.waitForTimeout(400)` (or wait for the explicit transitionend) before snapshotting any column-width measurement. Disabling that transition during user-driven drags (the `chatDragging` state in this story) is essential so the chat tracks the pointer 1:1 — without it, every pointermove would queue a 180ms ease.
  - **Stale-prop trap inside pointer event handlers.** The chat panel receives `chatWidth` as a prop, but inside `onPointerUp` you cannot use `chatWidth` directly to report the final width back to the parent — React's render-cycle means the prop is a stale closure value. Either (a) keep a `dragWidthRef` that's written from `onPointerMove` and read on `onPointerUp`, or (b) ALSO update an effect-mirrored ref of the prop (`chatWidthRef.current = chatWidth`). This story uses both: `dragWidthRef` for live drags, `chatWidthRef` for the keyboard handler since each keypress needs to read the latest committed value.
  - **`tabIndex={0}` + `role="separator"` + arrow-key handler is the canonical "draggable handle but accessible via keyboard" pattern** — no headless library needed. Don't forget `aria-orientation`, `aria-valuemin/max/now`, and an `aria-label` so screen readers announce it as a divider instead of an unlabeled separator. Each keypress should fire BOTH the live-update callback AND the persist-to-storage callback so users navigating purely by keyboard get persistence per-press, matching what pointer-up does for mouse users.
  - **Window-resize listener for "clamp on narrow viewports".** When a piece of layout state should react to viewport width but NOT persist transient narrow-viewport adjustments, mirror `window.innerWidth` into a state with a `resize` listener and derive an `effectiveX` value during render. Don't update the persisted state — the user's preference for the wide-viewport case is preserved untouched. This story uses `chatWindowWidth` exactly that way: at <600px viewport the rendered width clamps to `min(chatWidth, windowWidth - 320)` so the lesson column always has at least 320px, but `localStorage.lessonChat-width` stays at the user's chosen value.
  - **`position: relative` on a grid item is the simplest containing block for absolutely-positioned children inside that item.** Default grid items have `position: static`, so an `absolute` child escapes to the nearest positioned ancestor (often the viewport). Adding `position: relative` does NOT take the item out of grid placement — `gridColumn` / `gridRow` still apply. For the chat overlay's fullscreen mode, swap to `position: 'fixed'` to anchor to the viewport (matches the existing `asideExpandedStyle.position: fixed`); the handle isn't rendered in that mode so the containing-block question is moot for it.
